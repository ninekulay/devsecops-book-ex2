A.1.1 — สร้าง KV store ที่ implement read-your-writes consistency

เขียน in-memory KV store ใน Go/Rust/TypeScript ที่มี 3 node. Client write ไป node A → ต้องอ่านจาก node B/C ได้ค่าเดิม (ไม่ใช่ stale value). จะทำได้ยังไงโดยไม่ใช้ strong consistency?

// Approach: client carries "session token" = vector clock
// Every write returns a token (e.g., {nodeA: 5, nodeB: 3, nodeC: 4})
// Every read sends back the latest token
// Read node only serves request if its local clock >= token

// Pseudocode
type SessionToken = map[NodeID]uint64

// Client side
let myToken: SessionToken = {}

write(key, val) {
  res = sendToAnyNode({ key, val })
  myToken = max(myToken, res.token)  // merge
}

read(key) {
  res = sendToAnyNode({ key, ifAtLeast: myToken })
  // node compares its local clock; if behind, either:
  //   - reject (client retries another node), or
  //   - block until caught up (gossip)
  myToken = max(myToken, res.token)
  return res.value
}

// ทำไมนี่คือ "read-your-writes"
// client เขียน V1 → token = {A:5}
// client read หา node ที่ clock A >= 5
// → ไม่มีทางอ่าน V0 ได้

เรียนต่อ: เปรียบเทียบกับ Cassandra LOCAL_QUORUM read+write — ก็ใช้หลักนี้แต่ผ่าน quorum overlap ไม่ใช่ vector clock.

Architecture sketch:

type Raft struct {
  // persistent
  currentTerm int
  votedFor    int
  log         []LogEntry

  // volatile (all servers)
  commitIndex int
  lastApplied int

  // volatile (leader only)
  nextIndex  []int
  matchIndex []int

  state State  // Follower | Candidate | Leader
  electionTimer *time.Timer
}

func (rf *Raft) ticker() {
  for !rf.killed() {
    select {
    case <-rf.electionTimer.C:
      rf.startElection()  // become Candidate, RequestVote RPC
    case <-rf.heartbeatTicker.C:
      if rf.state == Leader {
        rf.broadcastAppendEntries()  // empty entries = heartbeat
      }
    }
  }
}

Pitfall ที่ทุกคนเจอ:

  • Lock contention — ใช้ sync.Mutex coarse-grained ตอนแรก, optimize ทีหลัง
  • Election timeout ต้อง random (150-300ms) ไม่งั้น vote split ตลอด
  • Term ต้อง update ก่อน state เปลี่ยน — order สำคัญ

A.3.1 — Implement SWIM-style gossip + simulate partition

เขียน gossip protocol ที่ 10 node sync membership view กัน. simulate network partition (block message ระหว่าง 2 group). วัดเวลา convergence หลัง partition ฟื้น

SWIM ในประโยคเดียว: ทุก node ทุก period (T): (1) ping random node, (2) ถ้า timeout, ขอ k node อื่น ping แทน, (3) ถ้ายัง timeout = mark suspected, (4) แชร์ membership update piggyback กับ ping packet ปกติ.

// Pseudocode (simplified)
class Node {
  members: Map<NodeId, MemberState>
  incarnation: number = 0

  async tick() {
    // 1. Direct ping
    const target = randomMember()
    const ok = await pingWithTimeout(target, 200ms)
    if (ok) return

    // 2. Indirect ping (via k=3 helpers)
    const helpers = randomMembers(3, exclude=[target])
    const indirectOk = await Promise.any(
      helpers.map(h => h.pingProxy(target, 200ms))
    )
    if (indirectOk) return

    // 3. Mark suspect
    this.members.set(target, { state: 'suspect', timestamp: now() })
    this.broadcastUpdate(target, 'suspect')
  }

  // After T_confirm, suspect → confirmed dead
}

// Gossip = piggyback membership delta on every ping

Lab setup: ใช้ Docker Compose 10 container, network namespace. Simulate partition ด้วย iptables DROP ระหว่าง 2 subnet. วัดเวลาตั้งแต่ partition ฟื้น → ทุก node เห็น membership ถูกต้อง.

A.4.1 — เขียน linearizability checker สำหรับ KV store ใน A.1

(1) เก็บ history ของทุก operation (start time, end time, type, args, result), (2) เขียน checker ที่หา linearization order ที่เป็นไปได้, (3) inject network partition แล้ว verify ว่า KV store ยัง consistent (หรือพิสูจน์ว่ามี bug)

Algorithm summary (Wing & Gong 1993):

  1. History = list of events: {op, args, result, t_invoke, t_return}
  2. Sort by t_invoke
  3. Brute-force หา permutation ที่: (a) preserve real-time order ของ non-overlapping ops, (b) ผลลัพธ์ตรงกับ sequential spec
  4. Optimization: backtracking + pruning (Porcupine paper จาก Anish Athalye)

Easier path: ใช้ github.com/anishathalye/porcupine (Go) แทนเขียนเอง. Focus ที่ history collection + fault injection.

A.5.1 — Distillation: อ่าน Dynamo paper แล้วเขียนสรุป 1 หน้า

Outline ที่ดี (ของ Dynamo):

  1. Problem: Amazon ต้องการ KV store ที่ "always writeable" — ยอมเสีย consistency ก่อน availability (CAP: AP)
  2. Key techniques (5 อัน):
    • Consistent hashing — เพิ่ม/ลด node ไม่ rebalance ทั้งโลก
    • Vector clock — track concurrent versions
    • Sloppy quorum + hinted handoff — survive partition
    • Anti-entropy with Merkle tree — sync replica
    • Gossip-based membership — ไม่มี master
  3. Trade-off ที่ Amazon ยอม: client ต้อง resolve conflict (ไม่ใช่ DB) — เพราะ business rule รู้ดีกว่า
  4. What I'd do differently in 2026: ใช้ CRDT แทน vector clock + last-write-wins
  5. Implementation hint: เริ่มที่ consistent hashing ring (50 LOC) → vector clock → quorum read/write → anti-entropy

B.2.1 — เขียน controller สำหรับ "ScheduledJob" CRD

สร้าง CRD ScheduledJob ที่ทำงานเหมือน CronJob แต่: (1) รัน job ใน timezone ที่กำหนด (ไม่ใช่ UTC), (2) มี notification webhook เมื่อ fail. เขียนด้วย kubebuilder. Deploy บน kind

# CRD type (api/v1/scheduledjob_types.go)
type ScheduledJobSpec struct {
  Schedule    string             `json:"schedule"`     // cron expression
  Timezone    string             `json:"timezone"`     // "Asia/Bangkok"
  Template    batchv1.JobTemplateSpec `json:"template"`
  WebhookURL  string             `json:"webhookUrl,omitempty"`
}

type ScheduledJobStatus struct {
  LastRunTime *metav1.Time `json:"lastRunTime,omitempty"`
  LastResult  string       `json:"lastResult,omitempty"`  // success | failed
  ActiveJob   *corev1.ObjectReference `json:"activeJob,omitempty"`
}

# Reconciler (controllers/scheduledjob_controller.go)
func (r *Reconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
  var sj batchv1.ScheduledJob
  if err := r.Get(ctx, req.NamespacedName, &sj); err != nil {
    return ctrl.Result{}, client.IgnoreNotFound(err)
  }

  loc, err := time.LoadLocation(sj.Spec.Timezone)
  if err != nil { return ctrl.Result{}, err }
  schedule, err := cron.Parse(sj.Spec.Schedule)
  if err != nil { return ctrl.Result{}, err }

  now := time.Now().In(loc)
  next := schedule.Next(now)

  // ถ้าถึงเวลา → spawn Job
  if shouldRunNow(sj.Status.LastRunTime, next, now) {
    job := buildJob(&sj)
    ctrl.SetControllerReference(&sj, job, r.Scheme)  // owner ref
    r.Create(ctx, job)
    sj.Status.LastRunTime = &metav1.Time{Time: now}
    r.Status().Update(ctx, &sj)
  }

  // ตรวจ active job
  if sj.Status.ActiveJob != nil {
    var job batchv1.Job
    r.Get(ctx, key, &job)
    if job.Status.Failed > 0 && sj.Spec.WebhookURL != "" {
      go sendWebhook(sj.Spec.WebhookURL, "failed", job.Name)
    }
  }

  return ctrl.Result{RequeueAfter: time.Until(next)}, nil
}

C.2.1 — เขียน bpftrace script หา "slow syscall"

เขียน script ที่: (1) trace syscall ทั้งหมดของ process, (2) วัด latency ของแต่ละ syscall, (3) แสดง histogram ของ syscall ที่ช้าที่สุด 10 อันดับ

#!/usr/bin/env bpftrace
// trace-syscall-latency.bt
// Usage: sudo bpftrace trace-syscall-latency.bt -c "node app.js"
//        หรือ: sudo bpftrace trace-syscall-latency.bt -p <PID>

BEGIN {
  printf("Tracing syscall latency... Ctrl-C to stop\n");
}

tracepoint:raw_syscalls:sys_enter
/comm == "node" || pid == $1/
{
  @start[tid] = nsecs;
  @sysname[tid] = args->id;
}

tracepoint:raw_syscalls:sys_exit
/@start[tid]/
{
  $delta = nsecs - @start[tid];
  @latency_ns[ksym(@sysname[tid])] = hist($delta);
  delete(@start[tid]);
  delete(@sysname[tid]);
}

END {
  print(@latency_ns);
  clear(@latency_ns);
}

C.4.1 — Optimize slow query: 2 วินาที → 20ms

มี Postgres query ที่ใช้ 2 วินาที. EXPLAIN ANALYZE บอก seq scan + nested loop. ใช้ความรู้: index, query rewrite, partial index, ทำให้ < 50ms

-- Slow query (ตัวอย่าง)
SELECT o.id, o.total, c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= '2026-04-01'
  AND o.status = 'paid'
ORDER BY o.created_at DESC
LIMIT 100;

-- Step 1: ดู plan
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) <query>;

-- จะเห็น:
--  Limit  (cost=145000.00..145000.25 rows=100)
--    ->  Sort  (actual time=2100ms..2105ms)
--          Sort Method: external merge Disk: 320MB   ← ปัญหา!
--          ->  Hash Join
--                ->  Seq Scan on orders  (rows=2,500,000)  ← ปัญหา!
--                      Filter: ((created_at >= '2026-04-01') AND (status='paid'))
--                      Rows Removed by Filter: 8,500,000
--                ->  Hash
--                      ->  Seq Scan on customers ...

-- Step 2: เพิ่ม index ที่ตรง predicate + sort
CREATE INDEX CONCURRENTLY idx_orders_status_created
  ON orders (status, created_at DESC)
  WHERE status = 'paid';   -- partial index

-- Step 3: Re-run EXPLAIN
--  Limit  (actual time=15..18ms)
--    ->  Nested Loop
--          ->  Index Scan using idx_orders_status_created
--                Index Cond: (status='paid' AND created_at >= '2026-04-01')
--                Limit: 100
--          ->  Index Scan using customers_pkey

-- Step 4: ถ้า customers join ยังช้า — covering index
CREATE INDEX idx_customers_id_email ON customers (id) INCLUDE (email);

-- จะใช้ Index Only Scan → ไม่ต้องอ่าน heap

Checklist debugging slow query:

  1. EXPLAIN ANALYZE BUFFERS — ตัวเลขจริง ไม่ใช่ EXPLAIN เฉยๆ
  2. Sort Method: external = ไม่มี index ที่ตรง ORDER BY
  3. Rows Removed by Filter เยอะ = ต้องการ index ที่ filter
  4. Heap Fetches มาก = ใช้ INCLUDE (covering index)
  5. ตรวจ pg_stat_statements view สำหรับ top slow queries

C.5.1 — Capacity model สำหรับ 100K RPS service

ให้ design API ที่รับ 100K RPS sustained, P99 < 200ms. คำนวณ: pod ต้อง ก%ของ CPU, RAM, DB connection pool, cache hit ratio ขั้นต่ำ. แสดงสมการ ไม่ใช่ guess

# Assumptions ที่ต้องวัด/รู้
- Per-request latency (median): 50ms
- Per-request CPU: 5ms (compute time)
- Per-request memory: 2MB (peak working set)
- Per-request DB call: 1 query, 8ms each
- Cache hit ratio: 80% (validate ด้วย load test)

# Application tier (Little's Law)
Concurrency = RPS × latency
            = 100,000 × 0.050s
            = 5,000 concurrent requests

# CPU capacity
Total CPU-seconds/sec = 100,000 × 0.005s = 500 CPU-seconds/sec
ที่ 70% util target → 500 / 0.7 = 714 vCPU
ถ้า node 16 vCPU → 714 / 16 = 45 nodes

# Memory
Per pod ≈ 5,000/pod_count × 2MB working set + base
ถ้า 100 pod → 100MB + 200MB base ≈ 300MB/pod
Total ≈ 30GB (อยู่ใน 45 node × 8GB ได้สบาย)

# DB capacity (cache miss)
DB QPS = 100K × (1 - 0.80) = 20,000 DB queries/sec
DB response time avg 8ms → concurrency = 20,000 × 0.008 = 160 conn
ใส่ buffer 2x → pool = 320 conn
แบ่ง 45 pod → 8 conn/pod (with PgBouncer)

# Cache (Redis)
Cache QPS = 100K (read every request)
Network bandwidth: each cache resp 1KB → 100MB/s = 800Mbps
Need 1Gbps NIC (Redis Cluster ถ้าเกิน)

# Headroom & safety
- Add 30% over computed = ป้องกัน traffic spike
- Multi-AZ → คูณ 1.5 (ทน 1 AZ ตาย)
- Final: ~70 nodes, 500 DB conn pool, 3 Redis shards

Critical insight: ตัวเลขที่คุณ "เดา" มักผิด 5-10x. ต้องวัดจริงจาก load test (k6, autocannon) ที่ ramp ขึ้นจน 100K RPS แล้วดูว่า bottleneck คืออะไรจริง — มักจะเป็น DB pool หรือ cache evict ก่อน CPU.

    - syft $IMAGE -o spdx-json > sbom.spdx.json

# Custom rule: /etc/falco/falco_rules.local.yaml
- rule: Suspicious Shell in Container
  desc: Shell spawned inside a production container
  condition: >
    spawned_process and container and shell_procs
    and not k8s_container_starts_with(c, "debug-")
  output: >
    Shell spawned in container
    (user=%user.name container=%container.name image=%container.image.repository
     proc=%proc.name pid=%proc.pid)
  priority: WARNING
  tags: [container, shell, mitre_execution]

- rule: Read of Sensitive Credential File
  desc: Process read /etc/shadow or kube secrets path
  condition: >
    open_read and (fd.name=/etc/shadow or fd.name startswith /var/run/secrets/)
    and not proc.name in (sshd, vault, agent)
  output: >
    Sensitive file read
    (user=%user.name file=%fd.name proc=%proc.cmdline container=%container.name)
  priority: CRITICAL
  tags: [filesystem, credentials, mitre_credential_access]

- rule: Outbound Connection to Non-Allowlist
  desc: Container made connection to IP outside allowed list
  condition: >
    outbound and container
    and not fd.sip in (allowed_outbound_ips)
    and not k8s_namespace in (egress_allowed_namespaces)
  output: >
    Suspicious outbound: %container.name -> %fd.sip:%fd.sport
    (image=%container.image.repository)
  priority: WARNING
  tags: [network, mitre_command_and_control]

เวลา: ตลอด track · Resource: TryHackMe, HackTheBox, OWASP WebGoat (legal!)
  • "Think like attacker" — understand exploit primitives
  • Lab on TryHackMe — เข้า Junior Penetration Tester path
  • Read CVE writeups, watch DEF CON talks
E.5.1 — Complete TryHackMe "Web Fundamentals" + write defensive PR

เรียน path "Web Fundamentals" บน TryHackMe (~30 ชม.). เลือก vuln type ที่เข้าใจดีที่สุด. หา code ในระบบที่ทำงาน → เขียน PR แก้ + เขียน blog "How I found and fixed X in our codebase"

Why offense-defense ต้องคู่กัน: ถ้าไม่เคยลอง exploit จริง คุณ ไม่ รู้ว่าจะป้องกันลึกแค่ไหน. ตัวอย่าง: รู้แค่ "SQL injection อันตราย" ≠ รู้ว่า WAF ตัวไหนบายปาส UNION-based ได้

Legal path (สำคัญ — อย่าทำผิดกฎหมาย):

  • TryHackMe / HackTheBox / OverTheWire — sandbox legal
  • OWASP WebGoat / DVWA — install บน laptop ตัวเอง
  • HackerOne / Bugcrowd — ลงทะเบียน bug bounty (มี scope ชัดเจน)
  • ห้าม: ทดสอบบนระบบที่ไม่ใช่ของตัวเอง โดยไม่มี written permission

Recommend learning order:

  1. Web (XSS, CSRF, SQLi, SSRF) — ใกล้เคียงงานจริงสุด
  2. Authentication / Authorization (JWT attacks, OAuth flaws)
  3. Container escape (CVE-2019-5736, etc.)
  4. Cloud misconfig (Pacu, ScoutSuite — สำหรับ AWS; PowerHuawei สำหรับ Huawei)

Deliverable: 1 defensive PR + 1 blog post + 5 active TryHackMe rooms completed.

Capstone — Track E

(1) Lead security review ของ 1 product feature ก่อน launch — present finding ต่อ leadership, (2) SLSA Level 2+ achieved with audit evidence, (3) ≥ 1 defensive contribution (PR, advisory, blog) ที่ public, (4) ทำ tabletop "data breach response" กับ legal + comms team.
